# Shared wallet implementation record

Implementation started from Center main `d5ec4af1877cca8d1dda806cdd217aa18b16b3b6` in the isolated `feat/shared-passkey-wallet` worktree. An inventory of local branches and worktrees confirmed that existing Center source work was already represented on main, including squashed deployment and sponsorship changes. Historical dev ancestry does not need merging. No remote push or production activation accompanies this checkpoint.

This is an experimental Base account profile and its verification foundation. It is not yet a usable shared wallet. The [strategy](CENTER-WALLET-PLAN.md) and [specification](CENTER-WALLET-SPEC.md) remain the delivery contract.

The pilot recovery configuration grants either owner full authority. Direct Safe withdrawal of its native balance works in the local experiment with Center unavailable and EntryPoint, adapter, signer and verifier code unavailable. It does not recover an EntryPoint deposit while EntryPoint is absent. Enrollment tests prove backup-key possession with a test EOA; consumer backup usability and independent storage remain unaccepted.

An unproven registration candidate does not reserve its credential ID globally. The verified mapping has unique RP/credential and current-primary wallet constraints, plus a deferred foreign key to its verified enrollment/account/user-handle tuple. Verification and challenge consumption roll back together when a concurrent credential claim loses. Verified identities and their original receipts survive ceremony expiry and cleanup; replay cannot restore a superseded primary credential. Pending-enrollment admission counts pending records only, while verified identities require durable storage capacity. A fresh deployment approval must resume the same verified enrollment and exact initialization.

These rotation proofs reject removed onchain owners and old setup approvals. Revocation of existing browser grants and Center sessions on rotation belongs to W5/W6 integration; the stable Safe principal does not implement that revocation by itself.

## Observability loop

Run [the required gate](CHECK-OBSERVATIONS.md) with Node 22, pinned Foundry and a disposable PostgreSQL 16 database:

```sh
npm run check:preflight
npm run check
```

The command prints `.generated/checks/<run-id>/summary.json`. Inspect its result, revision, dirty state, source attribution, individual step results and required-suite counts. The source must remain frozen during a full run. Logs and reports are ignored local artifacts; no secret environment values belong in committed fixtures. Read the failed step, reproduce the failure in its focused suite, fix it, then rerun the affected checks and the integration gate.

The observation runner now hashes actual file contents and modes against committed blobs, so Git clean filters and hidden index flags cannot conceal changes. Browser reports and screenshots are under `.generated/wallet-observations/browser-required/` and `browser-enrollment/`; their tier explicitly excludes physical-device claims. These are the last focused observations, not standalone claims that the full required gate passed.

Behavioral failure evidence includes the legacy EOA envelope rejecting contract signatures, incorrect base64url padding rejected by the actual upstream signer, legacy onboarding-method substitution rejected by the new profile, the old PostgreSQL authorization constraint rejecting the new explicit method, quota contention and process death. The signature ordering guard was removed in an isolated mutation copy; two tests then failed. These establish specific assertions, not complete test-suite mutation coverage. Initial missing-import failures are not counted as behavioral proof.

Two actual child processes exercise transaction rollback before commit and recovery after commit when the response is lost. Actual invalid EntryPoint submission is checked for no payment, deposit debit or nonce consumption. A local simulation alone is not recorded as a submitted transaction.

The enrollment browser gateway drops its response only after the replica returns from an awaited PostgreSQL commit. Chromium transparently retried that interrupted POST three times in the observed run. Every result referred to the original receipt, and a request through the second replica recovered the same identity. Another real assertion with user verification disabled failed without a credential mapping; a later verified assertion completed enrollment.

The enrollment race suite offers 100 identical candidate requests, 100 identical finalization requests, and 100 conflicting candidates across two actual processes with one database connection each. Identical requests retain one candidate and one original verification receipt; conflicting candidates produce one acceptance and 99 explicit conflicts. Reports under `.generated/wallet-observations/enrollment-races/` include stage latency and status counts. These bounded races do not qualify sustained throughput, overload recovery or deployment capacity.

Real PostgreSQL tests exposed an unsupported oversized regex quantifier during credential insertion and missing-field SQL checks that could evaluate to NULL. The migration now uses a bounded length check plus character validation, and requires JSON-dependent constraints to evaluate to true. The process fixture also needed callback-compatible pool reads; its initial hang was test infrastructure, not a production store deadlock.

An expiry test observes an actual PostgreSQL uniqueness-lock wait, releases the blocking insertion after the deadline, and verifies that the waiting finalization rolls back credential insertion and challenge consumption. Isolated mutations removing backup-owner equality and weakening RP/credential uniqueness both made their targeted tests fail; neither mutation changed the shared source tree.

Deployment codec tests first failed against a compiling registration-context/general-relay baseline, then passed with the distinct deployment document and exact envelope validation. Installed transaction parsing and signer recovery accepted several noncanonical RLP forms; canonical byte comparison rejects them without changing the bytes returned for later dispatch. A separate mutation test exposed caller-owned context changing during assertion access; proof verification now snapshots bounded trusted state first.

The general signed-transaction validator now accepts canonical zero fee quantities for legacy, EIP2930 and EIP1559 while rejecting malformed integer encodings, empty or nested signature scalars, and nested access-list storage keys. A genuine signature over a nested key can survive SDK parsing, reserialization and signer recovery; explicit address/key byte-string checks close that separate boundary. Valid nonempty access lists, including leading-zero keys, retain their original bytes. The deployment profile's positive-priority policy is unchanged.

Deployment journal tests observe real unique-index blocking across approval expiry, kill either process at durable boundaries, race differing valid signatures and retain the original nonce/allocation after recovery. Direct SQL cannot insert a claimed/signed row or skip the required phase transition. A post-write lease expiry rolls back signed-byte persistence. Shared-policy tests use two processes to race activation and callback removal against claims; a regression with different leading search-path schemas exposed an advisory-lock identity bug. Activation now locks by the resolved policy table OID. Input snapshots reject accessor/proxy changes across connection and lock waits.

The long-history test exposed an unpinned Anvil hardfork: its 32,000-block fixture spent roughly 115 seconds mining and 75 milliseconds inspecting. Selecting the same explicit Cancun target as the pinned contract proofs reduced mining to a few seconds. The 32,000 actual blocks, retained history, concurrency assertions and three-second inspector deadline are unchanged. This is a fixture correction, not a service throughput measurement.

## Next dependency

Connect the shared PostgreSQL deployment journal to immutable signed-transaction observation and recovery. A recovery check must permit expiry of the original consumed approval and inspect the stored template and exact winning bytes; fresh preflight must not replace its nonce, gas or fees. Complete reviewed Base fee accounting is required before dispatch can be enabled. Then add bounded signing transport, fenced dispatch attempts and canonical outcome/finality reconciliation. The local EntryPoint bootstrap experiment is not a hosted-bundler admission claim.

Shared Center login, typed app grants and core authority guards, operational trust-policy activation, PKCE app handoff, exact review UI, the shared connector, Beep/Money payments and native integration remain subsequent work. The strategy's sustained/burst/soak targets have not been run; concurrent correctness tests establish no throughput or production capacity claim. Keep legacy Para and external-wallet behavior available while these gates are completed.
