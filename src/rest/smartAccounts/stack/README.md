This directory contains source-bound contract artifacts for the Center smart-account integration. The JSON files include ABIs, creation/runtime bytecode, source provenance and runtime hashes. Historical observations in `evidence/` establish which code was seen at specific public-chain blocks; they do not establish the configuration of a user's account or enable execution by themselves.

`CenterSessionGuard` is local, undeployed Center code. It implements the legacy SmartSession `IUserOpPolicy` interface and has no owner, withdrawal, arbitrary-call or upgrade entry point. Its configuration is isolated by `(configId, multiplexer, account)`, matching the pinned policy storage convention. The calling SmartSession module must authenticate owner installation; anyone configuring their own multiplexer namespace gains no authority over another namespace.

The guard requires every session operation to name the exact configured paymaster with the approved runtime hash. Empty sponsorship data fails, so an accepted EntryPoint 0.7 operation does not ask the smart account to provide `missingAccountFunds`. It additionally restricts the pinned legacy Pimlico SingletonPaymasterV7 wire format to verifying mode: byte 52 is exactly 0, followed by the 12-byte validity window and 65-byte signature. Byte 1 selects ERC20 charging in this deployment and fails onchain. The newer upstream flag-byte interpretation does not apply to this runtime. Although the legacy parser mentions 64-byte signatures, its pinned OpenZeppelin recovery function accepts 65 bytes. The configured deployment must still be independently bound to that source, including its EntryPoint, signer and configuration authorities; a runtime match alone does not establish those properties. The guard does not approve tokens or authorize a token-charging paymaster.

The guard additionally requires canonical `execute(bytes32(0), bytes)` with one packed call. Existing action policies still bind its target, selector, arguments and native value; existing time policies still bind expiry. It accounts for verification, call, pre-verification, paymaster verification and post-operation gas, and bounds both fee fields. Its cumulative sponsored-cost counter uses requested gas multiplied by `maxFeePerGas`, conservatively bounding the EntryPoint prefund rather than estimating actual fees. Validation consumes counters even when the later inner execution fails.

The initializer is exactly 288 bytes: `abi.encode(address paymaster, bytes32 paymasterCodeHash, uint256 maxGasPerOperation, uint256 maxFeePerGas, uint256 maxPriorityFeePerGas, uint256 totalGasLimit, uint256 totalSponsoredCostLimit, uint128 maximumCalls, uint32 maxPaymasterDataLength)`. The matching `getConfig(bytes32,address,address)` returns that tuple and `uint256 gasUsed`, `uint256 costUsed`, `uint128 callsUsed`. The per-operation gas and fee caps fit `uint128`; sponsorship data and its configured length are exactly 130 bytes, and execution calldata is at most 8192 bytes. `maximumCalls` counts one canonical single call per accepted UserOperation. Multiple operations have separate signatures, nonces, sponsorship and receipts; they are not an atomic batch.

The existing `SimpleGasPolicy` artifact is retained as evidence, not used as a substitute for this guard. Its cost counter uses effective gas price, and it permits empty paymaster data. It therefore does not independently prevent max-fee-based account prefunding. `UsageLimitPolicy` counts UserOperations globally, which becomes a call count only when a separate constraint forbids batching.

Reproduce the guard with the pinned Solidity 0.8.28 compiler and Cancun target:

```sh
forge test --root src/rest/smartAccounts/stack
node src/rest/smartAccounts/stack/build-guard.mjs
node src/rest/smartAccounts/stack/verify-artifacts.mjs --write-manifest
```

`FORGE_BINARY` can select the local Forge executable. The build script verifies the compiler version and records the exact source SHA-256, original compiler-artifact SHA-256 and runtime Keccak-256. The checked artifact deliberately has `address: null` and `deploymentStatus: "undeployed"`. Production configuration must supply a verified deployment; the build does not deploy or broadcast.

Run `node src/rest/smartAccounts/stack/verify-artifacts.mjs` without the write flag to check all 17 artifact files, immutable substitutions, source binding for the guard, catalog file hashes and eight-chain historical coverage. `manifest.json` combines the component evidence and distinguishes the undeployed guard from observed existing deployments. Preserve artifact formatting: catalog hashes bind the complete checked-in artifact files, while upstream artifact hashes separately bind their original source.

`test/FullStack.t.sol` executes funded, cryptographically signed UserOperations through the actual EntryPoint, Safe proxy/factory, Safe7579, legacy SmartSession and policy runtimes. It deploys the exact pinned Pimlico creation bytecode with local fixture owners/signers, checks its resulting runtime hash, and signs the sponsor payload. The target terminal is explicitly a V6 `pay` ABI/caller/value fixture. These tests check payment budgets, sponsor-only gas, EntryPoint event identity and outcome, expiry, revocation, failed-execution counter retention, and rejection after the sponsor deposit is exhausted. They do not contact a hosted bundler/paymaster API or certify a production terminal deployment.

Activation requires a complete account inspector, exact installed policies and zero initial counters, a verified EntryPoint/account/module combination, and durable UserOperation transport. The reviewed owner setup may use SmartSession's explicit registry-bypass installation mode for exact pinned components, including the new guard; this is not an attestation. No session may enable generic ERC-1271 signing, account administration, fallback actions, module changes, allowances or permits. Revocation removes the session and advances its enable-signature nonce so an old enable signature cannot restore it.
